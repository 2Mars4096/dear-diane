# 56: Universal Organism and Cell Restructure

**Status:** not-started
**Goal:** Collapse the per-product organism / worker / validator inventory into one universal organism and one universal cell: fixed execution infrastructure and prompt architecture, with roles discovered by the orchestrator and task rules, prompts, budgets, tools, thresholds, sampling, and validation criteria supplied by typed role/brief/policy objects instead of per-variant builder functions, constants, fixed role catalogs, and substring-cue routers.

## Decisions

- One `WorkerDefinition` for every cell. No more `_build_live_website_worker`, `_build_live_generic_worker`, `_build_live_website_validator`, `_build_live_generic_validator`, etc.
- Cell system prompt is invariant ("you are an execution cell") and contains zero domain knowledge, thresholds, product rules, or task-family caps. It states only role identity, operating principles, constraint-following discipline, policy-following discipline, output-shape discipline, and graceful-fallback behavior.
- Prompt architecture is fixed; prompt content is flexible. The renderer owns stable sections, ordering, and slots (task, scope, constraints, evidence, tool policy, runtime policy, output contract, failure criteria, recovery hints), while orchestrator briefs fill those slots with task-specific text and policy values.
- Prompt context is centrally managed. The runtime tracks stable prompt architecture ids, constitution ids, tool/schema hashes, output-contract hashes, slot values, and dynamic snapshot refs so prompt-cache breaks and task-specific context changes are explicit.
- Roles are discovered by the orchestrator, not fixed by infrastructure. The orchestrator emits a `RoleSpec` / `WorkerBrief` graph with role labels, responsibilities, tool policy, prompt slots, output contracts, dependencies, and success criteria. "Builder", "reviewer", "researcher", "accessibility auditor", or "merge reducer" are examples of plan data, not hardcoded cell types.
- 100% of task-specific behavior moves into the orchestrator's brief, composed from a shared parameterized template library. The brief is the program; the cell is the interpreter.
- Validators stop being a code concept; they become a brief shape (read-only tool policy, reviewer-style output contract, failure criteria, and sampling policy) emitted by the orchestrator.
- The meta-orchestrator is the runtime control plane, not a constantly-running LLM chat. It owns the event loop, state reducer, ready queue, budget/policy gates, heartbeat/liveness tracking, decision log, and command queue. LLM orchestrator/reviewer calls are async proposal sources that the meta-orchestrator admits, rejects, or queues through deterministic policy.
- One universal organism replaces the per-product execution paths in `coding_execution`, `project_execution` (which today holds DAN Research execution), `super_organism` live lanes, `incident_execution`, and `reference_demo`. Different products differ by `OrganismPlan` shape, not by organism class.
- The migrated execution files are archived under `src/dan/worker/organisms/_archive/` rather than deleted outright, so trace replay and bug-fix back-porting still have access to the legacy stage-orchestration logic. Public exports in `worker/organisms/__init__.py` rebind to thin facades over `execute_universal_organism(...)` so external callers, CLI entry points, and tests do not break in one big step.
- Sampling is externalized to a brief-supplied policy object. `creative` and `deterministic` are only baseline profiles, not the complete set and not hard caps; briefs may override temperature, token budget, and related provider hints when the orchestrator has evidence that the task needs it.
- No infrastructure layer should encode fixed task limits such as required files, max worker counts, word/line limits, validation thresholds, timeout caps, or anti-template phrase lists. Those values belong in typed brief/plan policy data, with runtime safety bounds reserved only for provider limits, sandbox safety, and operator-configured budget ceilings.
- Agent lifecycle policy lives in the contract layer, reusing existing spawning/capability ceilings rather than becoming a separate orchestration queue: max depth, max live children, idle close, stale heartbeat timeout, resume/close semantics, and cancel propagation are explicit policy fields.
- Dispatcher stays deterministic. The substring-cue router (`_is_website_objective`, `_supports_live_execution`) and per-variant CLI builders consolidate behind a single `select_orchestrator(intent, context) -> OrchestratorChoice` function that resolves to a brief composer, not to an organism class. An LLM intent classifier remains a future-only option behind the same signature.
- The cell tool loop, model gateway dispatch, scheduler / contracts / policy, capsule bus, readiness signals, member-completion callbacks, and speculative validation stay where they are. This work touches only the prompt-assembly + organism-orchestration layers above them.
- High-frequency status updates are structured runtime events, not prompt turns: worker/tool start/finish, heartbeat, artifact/capsule emission, blockers, dependency unlocks, admissions/rejections, cancellations, and budget changes update the deterministic run state immediately. High-frequency semantic updates are allowed, but they are batched/async LLM observer outputs or worker self-status fields that become candidate decisions, never automatic authority.
- Queue settings should be centrally tunable but nonblocking by default: preserve lossless event/safety/command logs, while coalescing UI deltas and merging or dropping stale semantic-observer snapshots when the system is under pressure.

## Notes

- This work is a structural follow-up to `46-7` (worker bundle extraction) and the `54-*` DAN-v2 control-plane stack. It does not change the cell tool loop, the model gateway, or the scheduler — only what those substrates ingest.
- Concrete pain point that triggered this plan: `cli/super_organism.py` carries `_build_live_website_worker`, `_build_live_generic_worker`, `_build_live_website_validator`, `_build_live_generic_validator`, plus matching constants `_LIVE_WEBSITE_TOOL_IDS`, `_LIVE_GENERIC_TOOL_IDS`, `_LIVE_WEBSITE_FILES`, `_WEBSITE_TEMPLATE_PHRASES`, plus substring-cue router functions `_is_website_objective`, `_supports_live_execution`. Each new variant requires copy-paste-modify across all of these. The same shape recurs across `coding_execution.py`, `project_execution.py`, `incident_execution.py`, and `reference_demo.py`.
- The existing `_live_pacing_contract()` helper (a parameterized text snippet shared between worker `instruction` and `system_prompt`) points in the right direction, but the generalized form must take policy data from the brief. Defaults may exist as product policy profiles, but they are not universal constants.
- After landing this work, adding a "build a CLI tool" mode is one new brief composer in `worker/contracts/templates.py`, not a new organism + builders + constants + router cues.
- This is intentionally a refactor pass, not a redesign. `WorkerCoreExecutor`, `ToolLoopCompletionProvider`, `ExecutionRequest` / `OutputContract`, `ContextCapsule` plumbing, scheduler guardrails, and the durable conversation controllers (`*_conversation.py`) all stay as they are.
- The riskiest slice is `56-4`: `coding_execution.py` is ~3000 lines of scheduler/readiness/repair wiring that is the de-facto reference. Migration must preserve its behavior and emergent invariants while moving the implementation onto the shared substrate.
- Critical-path/dependency behavior should be inherited from earlier plans, not re-specified from scratch: Phase 1 graph edges and fan-out/fan-in, Plan 37 ready-queue dispatch and shared concurrency budgets, and Plan 55 agent-task DAG scheduling with capsule readiness unlocks.
- This is a full rebuild of organism execution on the universal-agent infrastructure. Legacy organism implementations are archived early as reference material, not treated as the code to keep mutating in place.
- Agent-to-agent prompt transfer is contract-first: orchestrators and upstream agents pass `RoleSpec`, `WorkerBrief`, `ContextPacket`, evidence refs, artifact refs, and output contracts. They do not pass opaque hand-written full prompts except as rendered debug artifacts in logs. The prompt renderer materializes the final provider prompt at the receiving cell boundary.
- API calls are not tied one-to-one to progress updates. Initial planning, worker execution, semantic observer/reviewer, repair, and final reducer calls are scheduled work items; routine status/event ingestion is local state reduction. A run should be able to emit many status events per second while making LLM calls only when a policy trigger or semantic-observer cadence admits one.
- Critical-path ready queues remain the main scheduling primitive. Parallel agents plus dependency/readiness blockers are enough for this rebuild; tool-operation queuing should stay at the policy/admission boundary unless logs prove a separate queue is needed.
- LLM-facing semantic snapshots are bounded projections of the run state. They never replace the full event log, which stays append-only and replayable.
