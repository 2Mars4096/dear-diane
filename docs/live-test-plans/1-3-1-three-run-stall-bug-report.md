## Decisions
- Use isolated `/tmp` workspaces for the fair runs; nested workspaces under the main repo were contaminated by parent git status and were not a valid benchmark setup.
- Keep the prompts human and short, and keep acceptance criteria separate as reviewer-only checks.
- Treat "no project files created before timeout" as a DAN Code runtime/product failure rather than a project-quality miss.
- Refine bug claims after follow-on probes instead of freezing the broader initial interpretation once new evidence arrives.

- **Refined failure taxonomy:**
- DAN Code is not universally unable to scaffold greenfield projects on the current `kimi-k2.5` setup. It can complete small scaffold, CLI, and small API tasks.
- The current failure boundary appears at heavier, more coordinated greenfield tooling/backend prompts such as `codemodx`, `taskforge`, `termboard`, and the larger notes-service variant.
- The new project planner is not a no-op. On heavy prompts it now consistently narrows the broad request into a milestone-scoped first objective before the bounded coding organism runs.
- The lightweight read-only worker guidance patch partially improved that lower seam: at least one heavy prompt (`codemodx`) now crosses from read-only worker discovery into aggregation/materialization on an empty workspace.
- That lower-seam improvement is now generalized further: the active-tool-set guardrail fires for both the internal-state probe (`codemodx`) and the generic-`web_search` drift (`taskforge`) during the frozen-pack rerun. `termboard` still stalled one round earlier, before the same finalize seam could fire.
- The DAN Code-side bounded completion budget and quiet-period heartbeat are now working in the live product path. The post-finalize wait no longer disappears into a silent `chat.completions.create(...)` hang; it emits `code.heartbeat`, then `model.timeout`, then a structured `provider_completion_timeout` fallback that lets later stages keep running.
- The heavy-task failure boundary is now split across three later seams rather than one silent wait:
- `codemodx` now reaches real file materialization but still loses the aggregation output contract after writing a milestone-1 scaffold.
- `taskforge` now reaches real service materialization and begins repair-scope test work, but still stops short of a validated milestone because repair/aggregation continuation keeps timing out before executable tests and background processing land.
- `termboard` still fails earlier than the others: even after repair decomposition and the timeout/heartbeat seam, it has not yet crossed into first-file materialization.
- The coding path still tolerated invalid tool decisions badly: one run used the wrong `web_search` argument shape, multiple runs attempted reads of files that did not exist yet instead of writing them, and broader prompts were more likely to stay trapped in research/speculative-read loops.
- The current coding path still let repeated no-write rounds continue until timeout instead of escalating to repair or failing fast with a clearer diagnosis.
- Human prompts are still not evaluated raw at the product membrane: DAN Code rewrote them into more prescriptive internal objectives and, in some runs, expanded the acceptance contract beyond the reviewer-supplied list.
- **Immediate next fixes to test:**
- Add a greenfield-workspace guardrail so, after prompt/checklist ingestion, repeated nonexistent-file reads or research-only loops trigger repair/failure instead of more browsing.
- Harden aggregation output-contract salvage so runs that materially wrote files do not still fail as `missing_output:candidate_id` / `missing_output:target_files`.
- Cap long repair-stage file-audit loops so repair attempts keep advancing from partial scaffolds into executable tests/processors instead of repeatedly rereading the same files until another timeout.
- Confirm `termboard` now crosses worker -> aggregation instead of waiting indefinitely on the next worker completion.
- Add a next repair/milestone test: after validation rejects milestone 1 for missing API/tests/docs, repair attempt 2 must route the validator repair scope into worker briefs instead of repeating the original milestone.
- Add an explicit `python -m package` / `__main__.py` verification gate for CLI-style milestones so a narrow parser-test pass cannot mask a broken executable module path.
- Reuse the runtime normalization strategy already added for `dan research` so common tool-shape drift is tolerated on the DAN Code path too.
- Treat "no files created" as an explicit validator/report signal so heavier prompt stalls can fail decisively before long API timeouts.
- Investigate what flips DAN Code from successful materialization on small scaffold/CLI/API tasks into speculative-read stalls on broader backend/tooling prompts, even after a milestone planner narrows the first slice.
