# Known Issues & Failed Approaches

## Open Bugs

- **Concierge context bleed can steer furnace-intent turns into prior writing trajectories (for example recurring "2026 report" framing).** Even with furnace intent guardrails, chat-mode turns can inherit unrelated project/task memory and produce prose summaries instead of strict session-control output. Mitigation landed: dedicated `dan-furnace` direct-control portal bypasses concierge. Remaining fix path: stronger context isolation for furnace-intent turns in chat mode (separate surface/session namespace and strict response contract validation).
- ~~**Long PDF reads in furnace timed out as a single blocking ingestion step (`Read timed out after 90s`).**~~ **FIXED 2026-03-16.** Furnace ingestion previously wrapped a full-source PDF read in one timeout window, so long papers could stall the entire source at once (especially with hybrid/vision-heavy pages). Fixed by chunking PDF reads by page range in `src/dan/server/routers/furnace.py` (default 20 pages per chunk), removing enforced read timeouts by default to match concierge long-read behavior, keeping an opt-in chunk timeout (`DAN_FURNACE_READ_CHUNK_TIMEOUT_SECONDS` > 0), aggregating chunk text progressively, and persisting chunk summaries in `{source_id}.chunks.json` alongside the aggregated `{source_id}.txt`.
- ~~**Web search grounding could stop after a snippet-only search, making live answers look hallucinated.**~~ **FIXED 2026-03-16.** `search_web` was marked satisfied after any successful `web_search`, `web_fetch`, or `http_request`, so a snippet-only `web_search` could clear the completion gate before the model had read any page content. `handle_web_search()` also flattened results into unnumbered text and silently swallowed page-fetch failures. Fix: web results are now numbered, `fetch_content=true` fetches the top two pages in parallel and reports failures, the global prompt plus post-tool follow-up enforce evidence-only live answers, and `search_web` stays pending until fetched page content (or equivalent grounded web evidence) exists.
- ~~**Queued follow-up messages in full Chat dropped their attachments, and some pasted screenshots rendered with blank names.**~~ **FIXED 2026-03-16.** `ChatPanel.tsx` queued only raw text while a response was streaming, so sending another message with appended files/screenshots lost the attachments when that queued turn auto-ran later. Separately, clipboard `File` objects can expose an empty `name`, which left composer chips and queued-message previews blank. Fix: the pending-queue model now preserves `File[]` attachments, queued auto-send restores them into `sendMessage()`, live-session `Push` is hidden for queued items that still require attachment transport, and screenshot/file labels now use the shared fallback resolver (`Pasted Image.png`, etc.) instead of trusting browser-provided names.
- ~~**Clipboard screenshots in desktop chat attached as pathless in-memory blobs, so the model could only see metadata instead of inspecting the actual image.**~~ **FIXED 2026-03-16.** Pasted images in Chat mode already reached the composer, but clipboard `File` objects often had no filesystem path, so backend attachment handling could not invoke `image_describe` against a real file. Fix: `editorChat.ts` now normalizes pathless attachments before send, `electron/main.ts` exposes `fs:writeTempAttachment`, and Electron persists clipboard/data-URL attachments into `app.getPath("userData")/chat-attachments` so pasted screenshots and pathless figures get a usable local path. Full Chat now also auto-attaches pasted images immediately instead of requiring a second accept click.
- ~~**Editor-side AI features and per-mode sidebars were still wired to a dead `/api/chat/editor/message` path, and chat attachment chips were UI-only.**~~ **FIXED 2026-03-16.** `ModeChatSidebar`, `InlineEdit`, `aiCodeActions`, `WritingPane`, `CodeCells`, and `PageSummary` were still calling the removed editor-only route, while `InlineCompletion` depended on an equally missing `/api/chat/editor/complete`. - ~~**Triage parse failures dropped action hints and sent short edit follow-ups into read-only detours.**~~ **FIXED 2026-03-16.** When the triage LLM returned unparseable JSON, `triage.py` fell back to a generic `ask` result with no route or `action_hints`, so `send_message_with_tools()` could not enforce `file_write` on turns like "update it". - ~~**"Maximum update depth exceeded" crash when opening a folder in Development mode.**~~ **FIXED 2026-03-15.** There were two separate loop sources. First, `useSyncWorkspaceMode` in `AppShell.tsx` subscribed to `getActiveWorkspace()` via Zustand selector, which returns a new object reference on every workspace store update (because `updateWorkspace` creates `{ ...w, ...updates }`). The effect depended on the whole workspace object and also called `updateWorkspace`, creating a cascade: update → new ref → effect fires → update → ... Fix: replaced `getActiveWorkspace()` selectors with primitive-field selectors (`activeWsId`, `activeWsLastMode`, `activeWsName`) so effect deps only change when the actual values change, not on every object re-creation. Also fixed the same pattern in `AppShell`'s render (only extracts `name`/`color`) and `ResearchMode`'s `LibrarySection`/`FurnacePanel` (extract specific `researchConfig` sub-fields). Second follow-up cause: `FileExplorer.tsx` `TreeNode` used `useCodeStore((s) => s.openFiles.map((f) => f.path))`, which creates a fresh array each render; in Zustand v5 this kind of derived selector can trigger `useSyncExternalStore` render loops when many tree nodes mount. Replaced it with a stable per-entry boolean selector (`some((f) => f.path === entry.path)`). Related ENOENT errors for `package.json` in opened folders are a separate non-fatal issue in the Electron main process file-read handler.

## Main Mechanisms & Key Modules Review (2026-03-15)

Review of core mechanisms and how they work together in tandem.

### Core Data Flows

**Chat → Concierge → Graph/Run:**
- `ChatManager` holds `graph_store`, `capability_context`; `CapabilityContext` has `graph_store`, `run_manager`, `chat_manager`, etc.
- Concierge dispatches to tier executors; tier executors call `chat_manager.send_message_with_tools()` directly.
- Capability handlers receive `CapabilityContext` with workflow_id, graph_store, run_manager.
- **Works well:** Handlers can load graphs, start runs, list experiences; chat gets graph context for prompts.

**Gateway → Planner:**
- `gateway/router.py` calls `planner.execute_plan(plan, user_text=goal)` and expects `exec_result.get("graph")`.
- `execute_plan` delegates to `execute_plan_direct` for `GenerateCodePlan` when `DAN_DIRECT_BUILD` is on.
- `execute_plan_direct` returns `{"workflow_id": ..., "graph_data": graph_data, ...}` — **uses `graph_data` not `graph`**.
- **Broken:** Gateway gets `None` for `graph` when direct build path is used; raises 422.

**Run Events → Chat Handoff:**
- `chat_complete` can carry `stream_channel_id` for a `run-*` channel; client reconnects to that channel for run output.
- `chat_message` handler: `/run` parses → `RunManager.start_run` → `_pipe_run_events` subscribes to run queue, pushes to `run-*` stream.
- **Works:** Run events flow from RunManager to chat stream; client sees both chat completion and run progress.

### Event Routing

**Two WebSocket paths:**
1. **Main WS** (`/ws`): `wsConnection` connects here; `eventRouter` subscribes to `wsConnection.on("*")`.
2. **Chat stream WS** (`/api/chat/{channel}/events`): Dedicated per chat/run channel; chat tokens, tool results, run events.

**Research mode events:**
- `eventRouter` routes `artifact_created`, `node_started`, `node_completed` → `dan:engine-event-raw` CustomEvents (only when `activeMode === "research"`).
- `useResearchEvents` listens for `dan:engine-event-raw` and bridges to `researchEventRouter` → research store.
- **Source:** Main WS receives events from `GlobalEventBus` / run engine broadcasts. Chat stream events are not forwarded to main WS.
- **Gap:** If a workflow run is started from chat (e.g. `/run` or build-then-run), run events go to the chat stream WS, not the main WS. Research mode would not receive `node_started`/`node_completed` for pipeline stage updates unless the backend also broadcasts to the main WS.

**Mode sync:** `useEventRouter` syncs `activeMode` from `useAppStore` to `eventRouter.setActiveMode()`. Mode switching is correct.

### Research QuickStart ↔ Backend

**Flow:**
- QuickStart actions call `dispatchResearchCommand("/research literature-review \"topic\"")` → `persistent-chat:send` CustomEvent.
- `PersistentChatBar` listens and sends to chat API.
- Backend receives plain text; no `/research` command handler exists — concierge treats it as natural language.
- QuickStart also sets `store.setPrimaryTab("editor")`, `store.togglePipeline()`, etc. — local UI state only.

**Gaps:**
- Pipeline stages in Research UI are local state; they do not auto-sync with backend run progress unless the backend emits `node_started`/`node_completed` to the main WS.
- No dedicated research workflow type; "literature review" is a conversational request that may or may not produce a structured workflow.
- Research events from `researchEventRouter` (artifact_created, distillation_progress) expect backend to emit; if those come from chat-stream-only paths, Research mode won't see them.

### CapabilityContext & Handlers

**Shared context:** `CapabilityContext` is built at startup; per-request copies are created with `workflow_id` set. Handlers have `graph_store`, `run_manager`, `chat_manager`, `event_bus`, etc.

**Works:** Run lifecycle, experience search, graph listing, publish, introspection — all wired.

**Missing:** `event_bus` is optional; if handlers emit to a bus that the main WS consumes, Research mode could receive events. Need to verify whether capability handlers emit to the main bus or only to chat stream.

## Phase 33 Eval Findings (2026-03-11)

### Root causes (33-5 triage)
- **Routing (fixed):** CONFIRM handler and META_GOAL classification blocked explicit build requests. Fixed via `_requested_mode_forces_solver_path` bypass and META_GOAL→WORKFLOW_BUILD override.
- **LLM API flakiness (open):** Empty classifier responses, codegen timeouts, internal errors. Primary cause of cross-run variance. Retry (33-8) helps but provider stability is external.
- **Server stability (open):** 0-event responses under sustained eval load; WebSocket keepalive timeout on long codegen. `--delay` and heartbeat mitigate.
- **Semantic underspec (33-7):** Structurally valid but useless graphs (p02: 2-node review loop, p08: 1-node equity). Quality gates now flag score <30.

### LLM classifier returns empty response
- **Symptom:** `LLM classifier returned unparseable response: ` in server.log — empty string
- **Root cause:** The micro-tier classifier model (MiniMax-M2.5 via custom API endpoint) returns empty responses, possibly due to API issues or model configuration
- **Impact:** All prompts fall through to keyword heuristic classifier, which has limited pattern coverage
- **Workaround:** Added classification override for explicit `mode=build` requests
- **Status:** Open — classifier model/API reliability is outside eval harness scope

### Server solver path hangs for 60s+ without producing graph
- **Symptom:** After classification succeeds and routes to solver, the server emits progress-ack pings but never produces a final response or graph mutation
- **Root cause:** The solver path makes LLM calls (via the configured API endpoint) that appear to hang or timeout silently
- **Impact:** 0% graph creation rate in pilot evaluation (first run); improved to 60% after routing fixes
- **Workaround:** Added 90s wall-clock timeout in eval runner
- **Status:** Open for some prompts — likely LLM API reliability/latency issue

### `ActionPolicy.CONFIRM` blocks solver path for explicit build requests
- **Symptom:** Complex "Build a multi-department..." prompts get classified as `META_GOAL` (estimated cost 2.0 > threshold 1.0), triggering CONFIRM handler that returns "Please confirm before I do that" — BEFORE the solver-path bypass runs
- **Root cause:** CONFIRM check at line 1979 executes before `_requested_mode_forces_solver_path()` at line 2036
- **Fix applied:** Added `not _requested_mode_forces_solver_path(msg.metadata)` to CONFIRM guard; extended classification override to also catch `META_GOAL` → `WORKFLOW_BUILD` for explicit build mode
- **Status:** Fixed

### `normalize_chat_mode("build")` maps to `"agent"`, losing mode signal
- **Symptom:** `CHAT_MODE_ALIASES = {"build": "agent", "mutate": "agent"}` means the concierge never sees the original requested mode
- **Fix applied:** Added `requested_mode` field to SurfaceMessage metadata preserving the pre-normalization mode
- **Status:** Fixed

## Known Limitations (Adapter)

- ~~**Telegram fleet could re-process bot-authored group messages and sometimes drop final replies.**~~ **FIXED 2026-03-10.** Two related issues: (1) in group chats, Telegram could surface bot-authored messages in shapes where the fleet did not see `from_user.is_bot=True`, so a bot's own outgoing greeting/answer could be re-consumed and re-dispatched, causing repeated "Hi again..." loops; (2) final reply delivery could fail with `telegram.error.BadRequest: Message to be replied not found` when the original message was no longer replyable, aborting the dispatch. Fixed by hardening fleet-side bot-author detection using known fleet bot usernames plus bot IDs, by pre-seeding the fleet dedup cache with outbound Telegram `message_id`s so echoed bot sends are dropped even if Telegram omits author metadata, and by retrying Telegram sends once without `reply_to_message_id` when that specific error occurs.
- ~~**Starting two Telegram fleet processes could trigger duplicate replies and `getUpdates` 409 conflicts.**~~ **FIXED 2026-03-10.** A second `dan-bot start-all` process could poll the same bot tokens concurrently, so Telegram would terminate one poller with `Conflict: terminated by other getUpdates request`, while users could still see duplicate replies during the overlap window. Fixed by adding a single-instance fleet startup lock at `~/.dan/telegram/fleet.lock`, stale-lock recovery, and a clean CLI error instead of allowing the second fleet to start.
- ~~**Telegram adapter spammed Bot API 400s for command registration and reactions.**~~ **FIXED 2026-03-10.** Two noisy-but-nonfatal adapter issues: (1) Telegram command registration was forwarding slash commands with hyphens (for example `/goal-status`), which `setMyCommands` rejects because Telegram command names must match `[a-z0-9_]{1,32}`; (2) chats that reject bot-set reactions would trigger the same `setMessageReaction` `400 Bad Request` on every status update. Fixed by filtering Telegram command menus to Telegram-safe names only, and by disabling reactions per chat after the first Telegram `BadRequest`.
- ~~**Telegram fleet dedup treated the same human group message as four different messages across bots.**~~ **FIXED 2026-03-10.** Fresh live traces showed the same user message hitting `scholar`, `engineer`, `quant`, and `chief` at the same instant, but each bot saw a different local `message_id`. Because fleet dedup only keyed on `(chat_id, message_id)`, all four callbacks survived dedup, all four routed to the default `chief` winner, and the group got four delayed `chief` replies plus four reaction attempts. Fixed by adding a bot-agnostic inbound dedup fingerprint for non-private Telegram messages while keeping the per-message-id cache for outbound bot echoes.
- ~~**Telegram fleet serialized all private-DM turns for a bot behind one chat-wide history lock.**~~ **FIXED 2026-03-10.** The fleet used `_conversation_thread_key(chat_id, thread_id, bot)` as both the server continuity key and the adapter-side history lock key. In private chats `thread_id` is always `None`, so every DM to the same bot collapsed to `chat_id:main:bot` and the `async with history_lock:` block held that lock across the full server request + streaming lifecycle. Result: unrelated private messages could sit behind one long-running turn even though the shared concierge dispatcher already knows how to queue same-project work and parallelize independent work. Reviewed the working WhatsApp Web path, which forwards inbound turns without an adapter-wide execution lock. Fixed by keeping the broad conversation key for server-side continuity, but splitting Telegram's local history/lock scope into reply-aware lanes: forum topics and non-private chats still use the chat/topic key, replies reuse the prior lane, and unrelated private-DM messages get independent lanes so they can start in parallel.
- ~~**Messaging surfaces could treat `progress_ack` as the final answer and show awkward `"Got it. <user text>"` echoes.**~~ **FIXED 2026-03-10.** The runtime emitted instant acknowledgments as `ChatCompleteEvent(detected_mode="progress_ack")`, but several consumers still treated any `chat_complete` as terminal. Result: some adapter collectors stopped before the real answer arrived, while other bridges forwarded the ack as if it were the final response. Fixed by treating `progress_ack` as non-terminal in shared stream consumers (`cli/adapter.py`, Telegram fleet non-streaming collector, `dan-chat`) and by suppressing standalone relay of `progress_ack` in `app.py`'s adapter bridge. Telegram/messaging instant-ack copy is now generic `"Working on it..."` instead of echoing the user prompt.
- ~~**RunHandler starts useless no-op runs on empty adapter graphs.**~~ **FIXED 2026-03-09.** When a user said "run it" via WhatsApp, the classifier routed to `RUN_CONTROL`, which started a workflow run on an empty graph — completing in 0.02s with zero tokens and no output. The user got "[DAN] Run started: run-..." but nothing useful happened. Fixed by: (1) `handle_start_run` now rejects empty graphs (no nodes) with a clear message, (2) `RunHandler` now falls back to `DirectTaskHandler` (LLM+tools) when `start_run` fails, giving the user a real AI response. Also reset the malformed `_adapter_swhatsappnet` graph (had orphan nodes, missing output ports on for_each sub-graph `summarize` node).

- ~~**WhatsApp responses contained raw HTML tags.**~~ **FIXED 2026-03-09.** `web_fetch` returned raw HTML from web pages, the LLM included it in responses, and the adapter sent it verbatim to WhatsApp. Fixed by: converting HTML to text in `web_fetch`, adding `strip_html_for_messaging()` to the adapter output path, and strengthening surface hints to forbid HTML.

- ~~**MutationPlan crashes when LLM nests `add_edge` fields inside `config`.**~~ **FIXED 2026-03-09.** LLM sometimes generates `{"op": "add_edge", "config": {"source_id": ..., "target_id": ...}}` instead of flat fields. `_normalize_generated_mutation_ops` didn't normalize `add_edge` ops. User saw "I hit an internal error" with a Pydantic ValidationError. Fixed by lifting edge fields from `config` to top level in the normalizer.

- ~~**Chat auto-mode detection crashes with `AttributeError: 'dict' object has no attribute 'graph_id'`.**~~ **FIXED 2026-03-09.** `_produce()` in `app.py` used attribute access on dict objects from `list_runs()`. Every `mode="auto"` request crashed instantly (15ms). Fixed to use dict `.get()` access.

## Known Limitations (Phase 15)

- **`dan-chat --local` still lacks real `meta_goal` delegation.** The local chat service factory builds a concierge without `meta_controller`, so `MetaGoalHandler` returns `"Meta controller not available."` in local mode even though server-backed concierge can delegate open-ended goals. Fix requires passing `meta_controller` through local chat service construction.
- **Multi-tool dispatch doesn't re-call LLM.** When the LLM returns multiple capability tool calls, results are formatted directly to the user without a second LLM round-trip for synthesis. Acceptable for V1 (low latency), but complex multi-tool scenarios may produce mechanical output.
- **Messaging adapter chat bridge is wired, but mutation-apply UX is incomplete on messaging surfaces.** Telegram/WhatsApp/email adapters can now route messages through `ChatManager` in chat mode, but when a mutation is proposed and `auto_approve=False` there is not yet a first-class follow-up command path that stores and applies the pending mutation cleanly. Today the bridge works best for read/query/run flows or auto-approve mode; reviewed mutation confirmation over messaging still needs a dedicated follow-up flow.
- **Concierge clarification fallback is still partial.** The runtime now persists pending confirmation/clarification state and can resume on `"yes"`, `"no"`, numeric selections, or a text match against an option. If the follow-up is still ambiguous after one round, it now auto-picks the first ranked option and proceeds; remaining gap: the fallback still relies on handler-provided option ordering instead of an explicit confidence score, and it does not add a true undo flow.
- **Meta-goal delegation starts sessions, but full meta-session streaming is still thin.** `meta_goal` now opens a real `MetaSession` through `MetaController`, links it to the project, and keeps the task active. Remaining gap: the concierge currently returns an immediate "meta session started" acknowledgment rather than streaming stage-by-stage meta events back to the surface.
- **Shared concierge file handling does not yet own surface-specific delivery.** The shared `FileHandler` can search and rank matches, but actual attachment/file-send behavior still lives in adapter-local wrappers. Server/local concierge flows return matched paths as text today; full attachment-aware follow-ups remain to be unified.
- **CLI `_bg_reader` and readline concurrency (resolved 2026-03-06).** Historical issue where background stdin reads could race main-thread `input()` (notably during `human_input_needed` prompts). Fixed with stdin lock + pause coordination in `dan-chat`; keep this note to avoid regressing the same pattern.

## Error Memory Migration Notes

When renaming workflows or moving error data between environments:

- **Collection naming**: `ErrorMemoryIndex` stores errors in vector collections named `dan_errors_{workflow_id}`. If a workflow is renamed (e.g. `_scratch` → `equity-research`), its error history stays under the old collection name. To migrate: export errors from old collection, re-index under the new name.
- **Global vs workflow scope**: `ErrorMemoryIndex.query()` with `scope="global"` scans ALL `dan_errors_*` collections. `scope="workflow"` searches only `dan_errors_{workflow_id}`. The `PrincipleStore` works similarly — `scope="global"` scans all workflow subdirectories in the memory store.
- **Cross-environment migration**: Error collections live in the vector store (memory/FAISS/Chroma). To move error history between machines: export the vector store data directory and the `memory/` filesystem store directory together. They are separate storage backends but both keyed by `workflow_id`.
- **Principle deduplication**: `PrincipleStore.load_principles(scope="global")` de-duplicates by principle `id` and keeps the highest-confidence version. If the same principle is stored under multiple workflow IDs, global scope merges them correctly.

## Known Limitations

- **reactFlowEdgeToDan can drop edge metadata (11-3):** When `rfEdge.data?.danEdge` is absent, the adapter creates a default DataEdge with `edge_type: "data"`, losing `edge_type` (control/context), `spread`, `context_key`, `mode`, `condition`. Ensure editor-created edges always preserve `danEdge` on `data`.
- **DEFAULT_OUTPUT_PORTS inconsistency (11-1):** Builder vs mutator disagree on composite (`result` vs `output`) and while_loop (`result` vs `output`). May cause port mismatches when mutator adds nodes. Future: extract to shared `dan.models.ports` or `dan.constants`.
- **TS NodeBase lacks read_set/write_set (11-1):** Python `NodeBase` has `read_set`/`write_set` for context declarations; `editor/src/types/graph.ts` omits them. Round-trip and ContextEdge validation may lose fidelity. Add to TS interfaces for parity.
- **Loader feature gaps (11-3):** Markdown loader emits only DataEdge; no ControlEdge or ContextEdge. Loader cannot define RAG, Validator, Reduce nodes. Round-trip via markdown loses control/context edges, artifact_refs, loop_groups. Use Python/JSON canonical source for full fidelity.
- **No graph validation in editor**: The frontend saves graphs without running the Python validation rules (`validate_graph`). Invalid graphs (missing entry points, broken edges) can be saved and will fail at run time. Validation feedback in the editor is a future enhancement.
- **Single-user only**: The run manager holds state in memory. Multiple browser tabs can connect to the same run via WebSocket, but there's no multi-user session isolation.
- ~~**No error feedback — silent API failures**~~: Resolved in Phase 3.5 — toast notification system added; all store actions wrapped in try/catch with error toasts.
- ~~**No loading states**~~: Resolved in Phase 3.5 — `loadingGraph`/`savingGraph` flags with spinners in `EditorToolbar`.
- ~~**No connection validation**~~: Resolved in Phase 3.5 — `isValidConnection` callback added in `GraphCanvas` (rejects self-connections, duplicates).
- **ConfigPanel is a generic field dump**: Iterates all non-skipped fields without logical grouping. JSON fields have a raw textarea with silent `JSON.parse` catch — no validation feedback. No way to add/remove/rename ports. (Partially improved: edge config is now editable with type-specific fields.)
- ~~**Fixed-height bottom panel**~~: Resolved in Phase 3.5 — resizable panels via `allotment`.
- ~~**Two header bars waste vertical space**~~: Resolved in Phase 3.5 — merged into single `EditorToolbar`.
- ~~**No keyboard shortcuts**~~: Resolved in Phase 3.5 — Cmd+S save shortcut added.
- **No undo/redo**: React Flow supports undo/redo via state snapshots, but it's not wired up yet.
- **App title/favicon are Vite defaults**: HTML title is "editor", favicon is `vite.svg`. Basic branding gap.
- **Node.js version warning**: Vite 7.x and `@vitejs/plugin-react` require Node.js 20.19+ or 22.12+. Current dev environment runs 20.17 — builds succeed with warnings but may break on future Vite updates. Fix: upgrade Node.js.
