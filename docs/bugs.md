# Known Issues & Failed Approaches

## Open Bugs

- ~~**Path-scoped creative tasks misrouted to FILE_REQUEST when message contained a filesystem path.**~~ **FIXED 2026-03-12.** Messages like "help me write a comprehensive supply chain report in tex" containing a filesystem path were classified as `FILE_REQUEST` at 0.9 confidence, bypassing the LLM classifier entirely and routing to `FileHandler` (file search) instead of the tool-using direct-task handler. Three compounding issues: (1) `_looks_like_path_write_request` only caught narrow patterns like "write...tex file" but missed natural phrasing ("help me write a report...in tex", "download and cite figures"); (2) the `has_path` fallback set 0.9 confidence, exceeding the LLM fast-path threshold; (3) verb-like words in filenames (e.g. "draft" in `draft.pdf`) could falsely override file-retrieval exclusions. Fixed by replacing the narrow function with `_looks_like_path_scoped_task` using 6 signal categories (help-me+action, format specifiers, multi-action instructions, creative verb+output noun, retrieval-start exclusion, path-stripped verb detection), lowering the `has_path` fallback confidence to 0.65, and stripping path content before checking creative verbs. 34 regression tests.
- ~~**Chat history titles were just raw first-prompt truncations, so tabs/threads looked noisy and repetitive.**~~ **FIXED 2026-03-12.** The editor created threads with a prompt slice as the visible title and there was no server-owned upgrade path, so history rows looked like raw message previews instead of stable conversation tabs. Fixed by adding `chat_titles.py`: the server keeps an immediate readable fallback, then asynchronously generates a better thread title from the first user message using the cheapest available model, while manual renames set a lock so auto-generation never overwrites user intent.
- ~~**Editor/full-screen chat could show an empty assistant bubble and never deliver any text when the dispatcher queued the turn.**~~ **FIXED 2026-03-12.** The server may emit `chat_queued` with a replacement `stream_channel_id` and then close the original WebSocket. The editor `ChatPanel` did not follow that handoff, unlike the eval client and messaging adapters, so queued requests looked like a blank placeholder assistant turn with no progress or final answer. Fixed by teaching the renderer to display a queue message, reconnect to the redirected channel, and continue consuming streamed events there.
- ~~**Desktop/editor chat could stop at "Working on it ..." and never show the real final answer.**~~ **FIXED 2026-03-12.** The concierge intentionally emits interim `ChatCompleteEvent`s with `detected_mode="progress_ack"` for reassurance/progress updates, but the React `ChatPanel` still treated every `chat_complete` as terminal and closed the WebSocket immediately. Fixed by treating `progress_ack` as non-terminal in the editor chat stream handler: the assistant bubble still updates with the interim status text, but the socket stays open until a real final `chat_complete`, mutation event, interruption, or error arrives.
- ~~**WhatsApp `_split_message()` could loop forever on long messages when the remainder started with a space.**~~ **FIXED 2026-03-12.** After a split on the last space before `max_len`, the code sliced `text = text[split_at:].lstrip("\n")`, which preserved the leading space. On the next iteration `rfind(" ", 0, max_len)` could return `0`, producing an empty chunk and never advancing. Fixed by treating `split_at == 0` as `max_len` and stripping both newlines and spaces from the remainder (`lstrip("\n ")`). This turned up during post-review testing of the WhatsApp retry/fallback path.
- ~~**Inline direct execution was wired to a nonexistent `capability_context.llm_provider` and a fresh bare `Engine`, so the 32-7 path silently fell back or lost tool/event support.**~~ **FIXED 2026-03-12.** The first pass of plan 32-7 set `concierge._llm_complete_for_intent` from `capability_context.llm_provider`, but `CapabilityContext` has no such field in the live app. It also created a brand-new `Engine(config=...)` during concierge construction, bypassing the shared `RunManager` executor registry, tool wiring, and human-input/event callbacks. Fixed by routing intent extraction through `Concierge._intent_llm_complete()` backed by `chat_manager._providers`, and by constructing inline engines from the shared `RunManager` stack at execution time.
- ~~**`/build` could pass through the registry without actually forcing build-mode routing.**~~ **FIXED 2026-03-12.** The override logic lived after `registry.resolve_handler()`, so the handler-less `/build` command returned early before setting `msg.metadata["requested_mode"]="build"`. Classification then saw raw `"/build ..."` text and could miss the workflow-build lane. Fixed by handling `/build` before handler resolution, stamping `requested_mode=build`, and stripping the slash-command prefix from `msg.text`.
- ~~**Telegram bot identity was injected as a history system message, competing with the concierge prompt.**~~ **FIXED 2026-03-12.** `telegram_fleet.py` prepended a per-bot system message into `history`, so adapter-authored persona/length rules competed with the concierge's unified system prompt. Fixed by sending structured `surface_context` (`identity` + `peers`) to the server and letting concierge handlers render that metadata as extra system instructions.
- ~~**Trivial direct-task turns paid the full concierge prep cost.**~~ **FIXED 2026-03-12.** Short drafting asks and direct live-lookups still ran memory retrieval, domain expertise fetches, artifact resolution, and guard scaffolding before reaching the same direct-task/conversation handlers. Fixed with a conservative simple-turn fast path that only activates when there are no pending follow-ups, active goals, attachments, or explicit build/plan modes.
- ~~**Single-word acknowledgement replies could still enter the concierge fast path.**~~ **FIXED 2026-03-12.** The fast path reused `_GREETING_TOKENS`, which intentionally includes brief reply-ish words like `yes`, `no`, `ok`, and `sure` for completion-guard leniency, but `_simple_message_fast_path_candidate()` only blocked multi-word `_FOLLOW_UP_PHRASES`. Result: some clarify/confirm replies could still be treated as trivial social turns and bypass heavy prep. Fixed by explicitly excluding short acknowledgement tokens from fast-path eligibility and adding guardrail regression tests.
- ~~**Telegram reply-chain text polluted the primary message body.**~~ **FIXED 2026-03-12.** `TelegramAdapter` prepended `[Replying to: "..."]` into the message text passed upstream, so unrelated historical quotes leaked into task labels, classifier input, and file-search queries. Fixed by forwarding the raw user text unchanged while keeping the replied-to text in `MessageContext.reply_to_text`.
- ~~**Path-scoped create/write requests were force-routed to `FILE_REQUEST`.**~~ **FIXED 2026-03-12.** Any message containing a filesystem path short-circuited to `FILE_REQUEST`, so asks like "create a new project folder under Dropbox/..." fell into `FileHandler` search/clarification instead of the tool-using action path. Fixed by letting stronger intents (workflow/meta-goal) win before raw-path fallback and by routing true path-scoped create/write requests to `DIRECT_TASK` while preserving `FILE_REQUEST` for plain read/review requests.
- ~~**Eval client did not follow chat_queued redirects.**~~ **FIXED 2026-03-12.** Same pattern as the Telegram fleet: when the dispatcher queues same-project requests, the server emits `chat_queued` with a replacement `stream_channel_id` and closes the original stream. The eval client was connecting only to the initial channel; when it closed after `chat_queued`, the client stopped and recorded ~5ms failures with `no_graph_created`. Fixed by making `stream_events()` follow redirects in a loop.
- ~~**Telegram fleet could lose queued replies after dispatcher redirected the stream channel.**~~ **FIXED 2026-03-10.** The fleet opened a WebSocket to the initial `/api/chat/{channel}/events` channel returned by `/api/chat/message`, but when same-project queueing kicked in the server emitted `chat_queued` with a replacement `stream_channel_id` and then closed the original socket. The fleet ignored that redirect, so users could see a progress bubble and then never get the real answer. Fixed by teaching both `_stream_with_edits()` and `_stream_collect()` to follow queued-channel redirects transparently.
- ~~**Explicit path references polluted scoped file searches and produced irrelevant clarifications.**~~ **FIXED 2026-03-10.** `FileHandler` correctly used explicit directory paths like `Dropbox/.../projects` to narrow `search_dirs`, but it still passed the full user sentence, including the raw filesystem path, into `search_local_files()`. That caused irrelevant token matches and responses like "Found 10 matches... Which file?" when the path was only meant as search scope. Fixed by stripping explicit paths from the ranking query for scoped searches and by labeling unique directory hits as `Found folder: ...`.
- ~~**`format_prefix()` called without required `project_label` in `_handle_model_command`.**~~ **FIXED 2026-03-10.** All 6 call sites in `_handle_model_command` (runtime.py) used `format_prefix()` without the required positional arg, causing `TypeError` when any `/model` command ran. Fixed by switching to `format_bare_prefix()` which needs no project scope.
- ~~**`msg.surface_id` in `/memory-confirm` and `/memory-reject` handlers.**~~ **FIXED 2026-03-10.** `SurfaceMessage` has no `surface_id` field — the correct field is `external_id`. Both `/memory-confirm` and `/memory-reject` handlers in `_handle_memory_command` (runtime.py) used the wrong attribute, causing `AttributeError`. Fixed to `msg.external_id`.
- ~~**Telegram dumped raw web_fetch content (image markdown, navigation links, ticker badges) directly to the user.**~~ **FIXED 2026-03-10.** `handle_web_fetch` returned up to 100KB of raw scraped page content with no sanitization. The LLM sometimes echoed this directly, flooding Telegram with `![Image](url)` blocks, dense `[Ticker](url)` navigation lists, and bare `.webp`/`.png` URLs. Fixed by adding `_sanitize_web_content()` (strips image markdown, bare image URLs, and navigation link blocks) and adding explicit Telegram surface hints matching the existing WhatsApp protections.
- ~~**File search fell back to broad ~/Dropbox when follow-up messages lacked an explicit path.**~~ **FIXED 2026-03-10.** `FileHandler._candidate_search_dirs()` only scanned user turns for path references. When a user said "the first folder, please review" (referencing a directory the bot had just mentioned), the regex found nothing in the vague user text, and search fell through to the default `[~/Dropbox, ~/Documents, ~/Desktop]` dirs. Fixed by also scanning assistant turns and the project summary for path clues.
- ~~**Infinite clarification loop: bot repeats "Before I proceed: I'm making some assumptions..." regardless of user reply.**~~ **FIXED 2026-03-11.** Two interacting bugs: (1) `solver.py` heuristic path set `assumptions=["Inferred from classification heuristic without LLM planning"]` — a system-internal note whose content words never overlap any user message, so `guard_understanding()` always flagged it as ungrounded. (2) When the user answered, the replay re-entered `_solver_path()` with no guard bypass, re-triggering the same ungrounded-assumption check and producing the same clarification — infinite loop. Fixed by clearing heuristic assumptions and adding guard bypass on clarification replays.
- **`/cost` and `/retry` access `ctx.project.thread_id` which doesn't exist on `Project`.** Both `_handle_cost_command` and `_handle_retry_command` in runtime.py reference `ctx.project.thread_id` after `context_resolver.resolve(msg)`, but the `Project` model has no `thread_id` field. These commands will `AttributeError` at runtime. Low priority since these paths are rarely exercised (cost/retry require chat-store wiring).
- ~~**Telegram showed "Working on it..." for every message, including instant greetings.**~~ **FIXED 2026-03-10.** Telegram's `compact` verbosity caused `_process_inner` to yield an eager `progress_ack` before the LLM even started, so trivial messages like "Hi" and "Hello" showed a visible "Working on it..." bubble. Fixed by removing the eager `progress_ack` yield and relying on the existing `process()` reassurance timer (5s delay). Quick replies that complete within the delay window never show an interim bubble; long tasks still get reassurance after 5s. Reassurance events are now properly marked as `progress_ack` so stream consumers treat them as non-terminal.
- **Telegram/WhatsApp long responses still lack full LLM-generated plan disclosure and result checkpoints.** 31-14's phase-transition events are now wired (context → execution phases emit live `progress_ack` events that edit the Telegram message in place), but plan disclosure (§3-3), result checkpoints (§3-5), pre-flight clarification questions (§4-2 through §4-4), and interactive checkpoint timeout/disconnect handling (§5-3, §5-4) are still not implemented.
- ~~**Queued Telegram/WhatsApp messages could be acknowledged and then never receive the real reply.**~~ **FIXED 2026-03-10.** The adapter bridge in `app.py` only handled immediate `chat_complete` events and dropped `chat_queued`, so queued same-project or overflowed messages never subscribed to the dispatcher response bus. Fixed by relaying queued response buses back through the adapter path, sending an immediate queue acknowledgment, hardening dispatcher overflow draining for chained overflowed projects, and pinning response buses while a consumer is attached so long queued waits do not silently switch producers to a replacement queue.

- **Phase 21 tracking briefly overstated how much live wiring was actually closed.** The core Phase 21 modules landed, but four integrations are still only partially wired in the live runtime: `/goal` currently stores/report state without invoking `GoalLoopExecutor`, proactive follow-up startup currently enqueues stale-task scans but does not emit schedule-result or run-completion triggers, progressive-response wiring currently initializes/scopes `ProgressSession` without yet driving phase transitions from runtime events, and computer-use currently exposes `/computer` policy commands/config without registering browser/desktop capability handlers. Keep these grouped under the open "Phase 21 live-wiring follow-ups" slice instead of treating Phase 21 as fully runtime-complete.
- ~~**`DAN_MEMORY_EXTRACTION_LLM=<model-name>` looked enabled in `.env` but live concierge chat still stored only episode memories.**~~ **FIXED 2026-03-10.** Two separate issues combined into the same user-visible failure. First, `MemoryExtractor.extract_with_llm()` only treated `DAN_MEMORY_EXTRACTION_LLM=1` as enabled, so concrete model values such as `claude-sonnet-4-6` were interpreted as "off" outside explicit callers. Second, concierge's async background fan-out still referenced the deleted `_try_heuristic_extraction` helper, so the live chat path silently skipped fact/preference extraction even after the sync fallback was wired to `extract_with_llm()`. Fixed by accepting either boolean enable values or explicit model names in `DAN_MEMORY_EXTRACTION_LLM`, routing both sync and async concierge memory extraction through `extract_with_llm()` with heuristic fallback, and re-verifying live that `/corrections` and `/adaptations` respond correctly while durable `fact`/`preference` items are written to the memory kernel.
- ~~**Project-only scheduled triggers could create a fresh project/task or fail persistence when the scheduled dispatch lost the original surface `external_id`.**~~ **FIXED 2026-03-10.** `ProjectContextResolver` first looked up `trigger_context.project_id` under `msg.external_id`, so a project-only scheduled dispatch using fallback IDs like `"scheduled-task"` could miss the stored project and fall through to normal new-project resolution. Even after resolution fallback, later `ProjectStore` writes still depended on the supplied surface key. Fixed by adding any-surface project/task lookup by `project_id` for trigger-context resolution and by making project-store fetches fall back across surfaces when a project id is known.
- ~~**`/progress` verbosity override was process-global.**~~ **FIXED 2026-03-10.** `handle_progress_command()` stored a single module-global verbosity override that `Concierge._process_inner()` reused for every request, so one user or surface could silently change progress rendering for unrelated active conversations. Fixed by scoping overrides to the requesting `external_id` while keeping the old default bucket for legacy direct callers and tests.
- ~~**`python_eval` result extraction is broken.**~~ **FIXED 2026-03-09.** The wrapper script used `{{`/`}}` in a non-f-string, producing literal double braces interpreted as set-of-dict (TypeError). Fixed by changing to single braces `{`/`}` in the plain string. xfail markers removed, tests now pass.

- **Vibe research LLM calls may fail with provider quota/auth errors**: External dependency issue (`vectorengine.ai` returning 401/403 such as `Token not provided` or `insufficient_quota`). Workflow currently continues with fallback-safe outputs, but strategy generation/backtests degrade when LLM nodes fail.

- ~~**Intent classifier misrouted messages containing "status" as a topic word to STATUS_CHECK handler.**~~ **FIXED 2026-03-10.** The classifier used bare `"status"` as a substring match for `STATUS_CHECK`, so any message containing the word "status" (e.g. "Panama canal expansion project status") was classified as a system status query at 0.95 confidence, regardless of context. Additionally, messages containing filesystem paths like `Dropbox/CUHK-phd/projects` were not detected early enough to route to `FILE_REQUEST`. Fixed by replacing greedy substring keywords with specific system-status phrases and adding early path-reference detection.

- ~~**Concierge LLM classifier could silently select an unsupported micro model on generic OpenAI-compatible endpoints, then fall back to brittle routing.**~~ **FIXED 2026-03-10.** The first `classify_intent_llm()` implementation auto-resolved a provider-tier "micro" model (`gpt-4o-mini` / Haiku / Flash) from registered provider names. On deployments that only expose a generic `default` provider backed by an OpenAI-compatible endpoint (for example `vectorengine.ai` serving `deepseek-v3.2` / `MiniMax-M2.5`), that logic could pick a provider-specific model string the endpoint did not support. The classifier call failed, routing silently fell back to heuristics, and topical requests could still hit old dead-end paths. Fixed by using the configured chat/default model as the classifier fallback whenever only the generic default provider is present, and by moving to a hybrid classifier that trusts strong heuristics before calling the LLM.

- ~~**Experience lookup could end the conversation with "No similar workflows found."**~~ **FIXED 2026-03-10.** `ExperienceHandler` returned the raw capability message when workflow-history lookup found no matches, which produced a dead-end user reply for open-ended questions like "have we done anything similar to a supply chain risk analysis before?" Fixed by falling back to a normal helpful chat response when history search returns no matches, while still preserving the "no matching saved workflows" context.

## Phase 33 Eval Findings (2026-03-11)

### Root causes (33-5 triage)
- **Routing (fixed):** CONFIRM handler and META_GOAL classification blocked explicit build requests. Fixed via `_requested_mode_forces_solver_path` bypass and META_GOAL→WORKFLOW_BUILD override.
- **LLM API flakiness (open):** Empty classifier responses, codegen timeouts, internal errors. Primary cause of cross-run variance. Retry (33-8) helps but provider stability is external.
- **Server stability (open):** 0-event responses under sustained eval load; WebSocket keepalive timeout on long codegen. `--delay` and heartbeat mitigate.
- **Semantic underspec (33-7):** Structurally valid but useless graphs (p02: 2-node review loop, p08: 1-node equity). Quality gates now flag score <30.

### LLM classifier returns empty response
- **Symptom:** `LLM classifier returned unparseable response: ` in server.log — empty string
- **Root cause:** The micro-tier classifier model (MiniMax-M2.5 via custom API endpoint) returns empty responses, possibly due to API issues or model configuration
- **Impact:** All prompts fall through to keyword heuristic classifier, which has limited pattern coverage
- **Workaround:** Added classification override for explicit `mode=build` requests
- **Status:** Open — classifier model/API reliability is outside eval harness scope

### Server solver path hangs for 60s+ without producing graph
- **Symptom:** After classification succeeds and routes to solver, the server emits progress-ack pings but never produces a final response or graph mutation
- **Root cause:** The solver path makes LLM calls (via the configured API endpoint) that appear to hang or timeout silently
- **Impact:** 0% graph creation rate in pilot evaluation (first run); improved to 60% after routing fixes
- **Workaround:** Added 90s wall-clock timeout in eval runner
- **Status:** Open for some prompts — likely LLM API reliability/latency issue

### `ActionPolicy.CONFIRM` blocks solver path for explicit build requests
- **Symptom:** Complex "Build a multi-department..." prompts get classified as `META_GOAL` (estimated cost 2.0 > threshold 1.0), triggering CONFIRM handler that returns "Please confirm before I do that" — BEFORE the solver-path bypass runs
- **Root cause:** CONFIRM check at line 1979 executes before `_requested_mode_forces_solver_path()` at line 2036
- **Fix applied:** Added `not _requested_mode_forces_solver_path(msg.metadata)` to CONFIRM guard; extended classification override to also catch `META_GOAL` → `WORKFLOW_BUILD` for explicit build mode
- **Status:** Fixed

### `normalize_chat_mode("build")` maps to `"agent"`, losing mode signal
- **Symptom:** `CHAT_MODE_ALIASES = {"build": "agent", "mutate": "agent"}` means the concierge never sees the original requested mode
- **Fix applied:** Added `requested_mode` field to SurfaceMessage metadata preserving the pre-normalization mode
- **Status:** Fixed

## Known Limitations (Adapter)

- ~~**Telegram fleet could re-process bot-authored group messages and sometimes drop final replies.**~~ **FIXED 2026-03-10.** Two related issues: (1) in group chats, Telegram could surface bot-authored messages in shapes where the fleet did not see `from_user.is_bot=True`, so a bot's own outgoing greeting/answer could be re-consumed and re-dispatched, causing repeated "Hi again..." loops; (2) final reply delivery could fail with `telegram.error.BadRequest: Message to be replied not found` when the original message was no longer replyable, aborting the dispatch. Fixed by hardening fleet-side bot-author detection using known fleet bot usernames plus bot IDs, by pre-seeding the fleet dedup cache with outbound Telegram `message_id`s so echoed bot sends are dropped even if Telegram omits author metadata, and by retrying Telegram sends once without `reply_to_message_id` when that specific error occurs.
- ~~**Starting two Telegram fleet processes could trigger duplicate replies and `getUpdates` 409 conflicts.**~~ **FIXED 2026-03-10.** A second `dan-bot start-all` process could poll the same bot tokens concurrently, so Telegram would terminate one poller with `Conflict: terminated by other getUpdates request`, while users could still see duplicate replies during the overlap window. Fixed by adding a single-instance fleet startup lock at `~/.dan/telegram/fleet.lock`, stale-lock recovery, and a clean CLI error instead of allowing the second fleet to start.
- ~~**Telegram adapter spammed Bot API 400s for command registration and reactions.**~~ **FIXED 2026-03-10.** Two noisy-but-nonfatal adapter issues: (1) Telegram command registration was forwarding slash commands with hyphens (for example `/goal-status`), which `setMyCommands` rejects because Telegram command names must match `[a-z0-9_]{1,32}`; (2) chats that reject bot-set reactions would trigger the same `setMessageReaction` `400 Bad Request` on every status update. Fixed by filtering Telegram command menus to Telegram-safe names only, and by disabling reactions per chat after the first Telegram `BadRequest`.
- ~~**Telegram fleet dedup treated the same human group message as four different messages across bots.**~~ **FIXED 2026-03-10.** Fresh live traces showed the same user message hitting `scholar`, `engineer`, `quant`, and `chief` at the same instant, but each bot saw a different local `message_id`. Because fleet dedup only keyed on `(chat_id, message_id)`, all four callbacks survived dedup, all four routed to the default `chief` winner, and the group got four delayed `chief` replies plus four reaction attempts. Fixed by adding a bot-agnostic inbound dedup fingerprint for non-private Telegram messages while keeping the per-message-id cache for outbound bot echoes.
- ~~**Telegram fleet serialized all private-DM turns for a bot behind one chat-wide history lock.**~~ **FIXED 2026-03-10.** The fleet used `_conversation_thread_key(chat_id, thread_id, bot)` as both the server continuity key and the adapter-side history lock key. In private chats `thread_id` is always `None`, so every DM to the same bot collapsed to `chat_id:main:bot` and the `async with history_lock:` block held that lock across the full server request + streaming lifecycle. Result: unrelated private messages could sit behind one long-running turn even though the shared concierge dispatcher already knows how to queue same-project work and parallelize independent work. Reviewed the working WhatsApp Web path, which forwards inbound turns without an adapter-wide execution lock. Fixed by keeping the broad conversation key for server-side continuity, but splitting Telegram's local history/lock scope into reply-aware lanes: forum topics and non-private chats still use the chat/topic key, replies reuse the prior lane, and unrelated private-DM messages get independent lanes so they can start in parallel.
- ~~**Messaging surfaces could treat `progress_ack` as the final answer and show awkward `"Got it. <user text>"` echoes.**~~ **FIXED 2026-03-10.** The runtime emitted instant acknowledgments as `ChatCompleteEvent(detected_mode="progress_ack")`, but several consumers still treated any `chat_complete` as terminal. Result: some adapter collectors stopped before the real answer arrived, while other bridges forwarded the ack as if it were the final response. Fixed by treating `progress_ack` as non-terminal in shared stream consumers (`cli/adapter.py`, Telegram fleet non-streaming collector, `dan-chat`) and by suppressing standalone relay of `progress_ack` in `app.py`'s adapter bridge. Telegram/messaging instant-ack copy is now generic `"Working on it..."` instead of echoing the user prompt.
- ~~**RunHandler starts useless no-op runs on empty adapter graphs.**~~ **FIXED 2026-03-09.** When a user said "run it" via WhatsApp, the classifier routed to `RUN_CONTROL`, which started a workflow run on an empty graph — completing in 0.02s with zero tokens and no output. The user got "[DAN] Run started: run-..." but nothing useful happened. Fixed by: (1) `handle_start_run` now rejects empty graphs (no nodes) with a clear message, (2) `RunHandler` now falls back to `DirectTaskHandler` (LLM+tools) when `start_run` fails, giving the user a real AI response. Also reset the malformed `_adapter_swhatsappnet` graph (had orphan nodes, missing output ports on for_each sub-graph `summarize` node).

- ~~**WhatsApp responses contained raw HTML tags.**~~ **FIXED 2026-03-09.** `web_fetch` returned raw HTML from web pages, the LLM included it in responses, and the adapter sent it verbatim to WhatsApp. Fixed by: converting HTML to text in `web_fetch`, adding `strip_html_for_messaging()` to the adapter output path, and strengthening surface hints to forbid HTML.

- ~~**MutationPlan crashes when LLM nests `add_edge` fields inside `config`.**~~ **FIXED 2026-03-09.** LLM sometimes generates `{"op": "add_edge", "config": {"source_id": ..., "target_id": ...}}` instead of flat fields. `_normalize_generated_mutation_ops` didn't normalize `add_edge` ops. User saw "I hit an internal error" with a Pydantic ValidationError. Fixed by lifting edge fields from `config` to top level in the normalizer.

- ~~**Chat auto-mode detection crashes with `AttributeError: 'dict' object has no attribute 'graph_id'`.**~~ **FIXED 2026-03-09.** `_produce()` in `app.py` used attribute access on dict objects from `list_runs()`. Every `mode="auto"` request crashed instantly (15ms). Fixed to use dict `.get()` access.

- ~~**Auto-mode picked the wrong run status when multiple runs existed for one workflow.**~~ **FIXED 2026-03-10.** Both server and local chat were checking the first matching run from `RunManager.list_runs()` rather than the newest one, so an older run could incorrectly force or suppress `debug` mode. Fixed by adding shared `recent_run_failed_for_workflow()` logic in `chat_manager.py` that selects the latest matching run by `started_at` and supports both dict snapshots and older object-style entries. Covered by focused regressions in `tests/test_server/test_auto_mode.py` and `tests/test_server/test_chat_local_auto_mode.py`.

- ~~**WhatsApp paper summary returned raw PDF text.**~~ **FIXED 2026-03-09.** Two root causes: (1) `FileHandler._review_document` embedded 12,000 chars of raw PDF text in the user message and called `send_message` (no tools), but `UNIFIED_SYSTEM_PROMPT` rule #2 says "NEVER summarize a file you haven't read — call pdf_read first." Since no tools were available, the LLM was confused and could output the raw text verbatim. (2) `SURFACE_HINTS` for WhatsApp mentioned "never include raw HTML from web_fetch" but said nothing about pdf_read text. Fixed by: (a) `_review_document` now strips the adapter-generated "Please review this PDF: /path" prefix and "[User sent file: ...]" lines via `_extract_user_intent()`, and uses truthful "full text" vs. "truncated excerpt" wording; (b) `ChatManager.send_message()` / `_build_messages()` now support `extra_system_instructions`, and the WhatsApp PDF-review path uses a system-priority override that inline document text already counts as read source material; (c) `SURFACE_HINTS` for `whatsapp` and `whatsapp-web` now add "Never reproduce raw extracted text from pdf_read or file_read — always produce a structured summary or answer." Covered by focused regressions in `tests/test_server/test_whatsapp_document_review.py`.

- **Adapter heuristic classifier is keyword-only.** `_classify_adapter_intent()` uses keyword matching, not LLM intent classification. It handles common patterns (file requests, continuations, workflow build) but will miss nuanced intent (e.g. "remember that analysis we did last month" should probably search experience, but routes to conversation). The full fix is 25-6 (intent dispatcher with LLM fallback).
- **Adapter file search is filename-only, not content-aware.** `_search_local_files()` now normalizes separators (`space`/`_`/`-`) and ranks token matches, so natural-language queries match filenames more reliably, but it still searches filenames only. It will not find a file based purely on content inside the document.

- **LLM fabricates live data (prices, stats) in ask/conversation mode.** When a message doesn't match the keyword classifier for `direct_task` (e.g., "close price" instead of "stock price"), it routes to `conversation` → `ask` mode, which is text-only with no tools. The LLM then invents plausible-looking data from stale training knowledge. Historical stop-gap was an ask-mode honesty guard; the current structural direction is plan [25-12](plans/25-12-tool-aware-conversation.md) plus the unified prompt/text-only override path so unsupported live-data requests are answered honestly instead of fabricated.

## Known Limitations (Phase 15)

- **`dan-chat --local` still lacks real `meta_goal` delegation.** The local chat service factory builds a concierge without `meta_controller`, so `MetaGoalHandler` returns `"Meta controller not available."` in local mode even though server-backed concierge can delegate open-ended goals. Fix requires passing `meta_controller` through local chat service construction.
- **Multi-tool dispatch doesn't re-call LLM.** When the LLM returns multiple capability tool calls, results are formatted directly to the user without a second LLM round-trip for synthesis. Acceptable for V1 (low latency), but complex multi-tool scenarios may produce mechanical output.
- **Messaging adapter chat bridge is wired, but mutation-apply UX is incomplete on messaging surfaces.** Telegram/WhatsApp/email adapters can now route messages through `ChatManager` in chat mode, but when a mutation is proposed and `auto_approve=False` there is not yet a first-class follow-up command path that stores and applies the pending mutation cleanly. Today the bridge works best for read/query/run flows or auto-approve mode; reviewed mutation confirmation over messaging still needs a dedicated follow-up flow.
- **Concierge clarification fallback is still partial.** The runtime now persists pending confirmation/clarification state and can resume on `"yes"`, `"no"`, numeric selections, or a text match against an option. If the follow-up is still ambiguous after one round, it now auto-picks the first ranked option and proceeds; remaining gap: the fallback still relies on handler-provided option ordering instead of an explicit confidence score, and it does not add a true undo flow.
- **Meta-goal delegation starts sessions, but full meta-session streaming is still thin.** `meta_goal` now opens a real `MetaSession` through `MetaController`, links it to the project, and keeps the task active. Remaining gap: the concierge currently returns an immediate "meta session started" acknowledgment rather than streaming stage-by-stage meta events back to the surface.
- **Shared concierge file handling does not yet own surface-specific delivery.** The shared `FileHandler` can search and rank matches, but actual attachment/file-send behavior still lives in adapter-local wrappers. Server/local concierge flows return matched paths as text today; full attachment-aware follow-ups remain to be unified.
- **CLI `_bg_reader` and readline concurrency (resolved 2026-03-06).** Historical issue where background stdin reads could race main-thread `input()` (notably during `human_input_needed` prompts). Fixed with stdin lock + pause coordination in `dan-chat`; keep this note to avoid regressing the same pattern.

## Error Memory Migration Notes

When renaming workflows or moving error data between environments:

- **Collection naming**: `ErrorMemoryIndex` stores errors in vector collections named `dan_errors_{workflow_id}`. If a workflow is renamed (e.g. `_scratch` → `equity-research`), its error history stays under the old collection name. To migrate: export errors from old collection, re-index under the new name.
- **Global vs workflow scope**: `ErrorMemoryIndex.query()` with `scope="global"` scans ALL `dan_errors_*` collections. `scope="workflow"` searches only `dan_errors_{workflow_id}`. The `PrincipleStore` works similarly — `scope="global"` scans all workflow subdirectories in the memory store.
- **Cross-environment migration**: Error collections live in the vector store (memory/FAISS/Chroma). To move error history between machines: export the vector store data directory and the `memory/` filesystem store directory together. They are separate storage backends but both keyed by `workflow_id`.
- **Principle deduplication**: `PrincipleStore.load_principles(scope="global")` de-duplicates by principle `id` and keeps the highest-confidence version. If the same principle is stored under multiple workflow IDs, global scope merges them correctly.

## Known Limitations

- **reactFlowEdgeToDan can drop edge metadata (11-3):** When `rfEdge.data?.danEdge` is absent, the adapter creates a default DataEdge with `edge_type: "data"`, losing `edge_type` (control/context), `spread`, `context_key`, `mode`, `condition`. Ensure editor-created edges always preserve `danEdge` on `data`.
- **DEFAULT_OUTPUT_PORTS inconsistency (11-1):** Builder vs mutator disagree on composite (`result` vs `output`) and while_loop (`result` vs `output`). May cause port mismatches when mutator adds nodes. Future: extract to shared `dan.models.ports` or `dan.constants`.
- **TS NodeBase lacks read_set/write_set (11-1):** Python `NodeBase` has `read_set`/`write_set` for context declarations; `editor/src/types/graph.ts` omits them. Round-trip and ContextEdge validation may lose fidelity. Add to TS interfaces for parity.
- **Loader feature gaps (11-3):** Markdown loader emits only DataEdge; no ControlEdge or ContextEdge. Loader cannot define RAG, Validator, Reduce nodes. Round-trip via markdown loses control/context edges, artifact_refs, loop_groups. Use Python/JSON canonical source for full fidelity.
- **No graph validation in editor**: The frontend saves graphs without running the Python validation rules (`validate_graph`). Invalid graphs (missing entry points, broken edges) can be saved and will fail at run time. Validation feedback in the editor is a future enhancement.
- **Single-user only**: The run manager holds state in memory. Multiple browser tabs can connect to the same run via WebSocket, but there's no multi-user session isolation.
- ~~**No error feedback — silent API failures**~~: Resolved in Phase 3.5 — toast notification system added; all store actions wrapped in try/catch with error toasts.
- ~~**No loading states**~~: Resolved in Phase 3.5 — `loadingGraph`/`savingGraph` flags with spinners in `EditorToolbar`.
- ~~**No connection validation**~~: Resolved in Phase 3.5 — `isValidConnection` callback added in `GraphCanvas` (rejects self-connections, duplicates).
- **ConfigPanel is a generic field dump**: Iterates all non-skipped fields without logical grouping. JSON fields have a raw textarea with silent `JSON.parse` catch — no validation feedback. No way to add/remove/rename ports. (Partially improved: edge config is now editable with type-specific fields.)
- ~~**Fixed-height bottom panel**~~: Resolved in Phase 3.5 — resizable panels via `allotment`.
- ~~**Two header bars waste vertical space**~~: Resolved in Phase 3.5 — merged into single `EditorToolbar`.
- ~~**No keyboard shortcuts**~~: Resolved in Phase 3.5 — Cmd+S save shortcut added.
- **No undo/redo**: React Flow supports undo/redo via state snapshots, but it's not wired up yet.
- **App title/favicon are Vite defaults**: HTML title is "editor", favicon is `vite.svg`. Basic branding gap.
- **Node.js version warning**: Vite 7.x and `@vitejs/plugin-react` require Node.js 20.19+ or 22.12+. Current dev environment runs 20.17 — builds succeed with warnings but may break on future Vite updates. Fix: upgrade Node.js.
